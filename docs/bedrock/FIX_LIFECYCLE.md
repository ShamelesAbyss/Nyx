## LIF-06 implementation and conservative tradeoffs

The implementation remains manager-owned rather than putting an indefinite server into the finite terminal operation journal. `savePendingLaunch` commits a guest-scoped token/mode/container with a global guest namespace fence, empty session PID/start identity and an unset guest-shutdown-evidence bit **before** calling `runProotDetached` or `dispatchPersistentProot`. A failed/throwing checkpoint cannot dispatch. An acknowledgement does not establish server success; PID/API observations are separate. The fence survives post-dispatch exceptions, cancellation and failed identity enrichment. The optimistic detached-to-foreground fallback was removed: an “unsupported option” message alone is not proof no side effect occurred. The host launch's automatic second attempt was also removed; a timeout or missing callback cannot authorize retry.

UI and host service may have separate manager objects in one process. A shared lifecycle mutex serializes their manager operations; a shared checkpoint monitor/token check rejects stale session updates and shutdown-evidence writes. Saved guest evidence pins recovery to its namespace. Legacy guest session keys, malformed/partial fences and multiple namespaces block automatic launch, not silently become “no ownership.” SharedPreferences commit failures retain a same-process uncertainty latch, because a failed commit may still publish its edit in memory. Actual multi-process preferences coordination is not provided or claimed.

A guest log first-line token must match the saved token; an answering API alone is adoption, never stop authority. Guest stop additionally checks that token and the exact PID/start record in the command that signals, checks the exact `ollama serve` argv shape, and uses the existing kernel-start rechecks before TERM/KILL. A completion marker is not enough: both host and guest clean-stop paths independently probe whether the recorded process identity ended. A failed/empty/cancelled probe cannot establish this evidence.

The old `proot-distro kill <bare PID>` teardown lacks an atomic token/start-identity argument. This repair deliberately sends **no session-tree teardown** rather than pretending a separate preflight removes that race or proves every descendant stopped. It clears a guest session only after separately persisted guest-process exit evidence and a successful explicit absence observation for a previously token-bound session PID/start identity. Missing PID/start, live or reused PID, failed probe and foreground fallback without visible session identity all refuse within the existing finite command/poll bounds; none returns fake success. Readiness failure and refresh no longer discard the unresolved session evidence. An unused marker-only cleanup helper was removed.

This restriction can leave a legitimate foreground fallback or a detached session whose command line does not expose the token **permanently fenced in the current automatic paths**, even after external cleanup. The narrow patch adds no user-confirmed reset or new identity-recovery subsystem. Availability is intentionally sacrificed instead of signalling an adopted/unproven process or replaying a possibly live server. A separately authorized reconciliation/reset design would need its own evidence and ownership contract.

Host service changes are limited to notifier draining and explicit documentation that foreground timeout/destruction/callback cancellation ends service lifetime, not external ownership. There is no new promise that Android keeps an external server alive or stops it.
