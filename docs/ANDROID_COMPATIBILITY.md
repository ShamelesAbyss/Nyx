# Android compatibility for NYX 0.6.0

NYX 0.6.0 uses `compileSdk = 37`, `targetSdk = 37`, `minSdk = 26`, and `versionCode = 6`. The native release ABI is `arm64-v8a`. The official sources below were checked on **2026-11-12 UTC**. These are build requirements and implementation guidance, not evidence of device testing.

## Supported build stack

Android's current API-level compatibility matrix specifies **AGP 9.1.1 as the minimum for API 37.0**. The AGP 9.1.1 release notes explicitly support API 37.0 and below, require Gradle 9.3.1 and JDK 17 or newer, set SDK Build Tools 36.0.0 as minimum/default, set NDK 28.2.13676358 as default, and require Kotlin Gradle plugin 2.2.10. NYX pins this stack rather than using an unsupported older AGP plus a warning-suppression flag. The setup page currently contains older AGP 8.9.0-rc01 guidance; the newer, API-specific compatibility matrix and 9.1.1 release notes govern this choice. [1] [2] [3]

The root build uses AGP 9.1.1 with built-in Kotlin and Compose compiler 2.2.10. The separate Android Kotlin plugin and obsolete kotlinOptions block are removed; the JVM target derives from Java 17 compileOptions. The initially selected KSP 2.2.10-2.0.2 failed its source-set configuration, and Room 2.6.1 then failed KSP2 processing. Final pins are **KSP 2.3.6 and Room 2.8.5**; the temporary source-set suppression was removed. The full clean build and 212 JVM tests passed with this configuration. See `BUILD_COMPATIBILITY_FIXES.md` for reproduced errors and the Room/KSP release sources. Applying the old Android Kotlin plugin alongside built-in Kotlin fails with a duplicate-extension/plugin error. [2] [4] [14]

Android documents a temporary escape hatch for lower Kotlin versions: opt out of both built-in Kotlin and the new DSL, then strictly pin the old KGP/KSP classpath. That is not the chosen default, is not required for this project, and would introduce extra migration debt. The upgrade here is necessary for the selected built-in-Kotlin stack, not a claim that every possible AGP 9 opt-out configuration with Kotlin 2.0 was compiled and found to fail. [4] [14]

The Gradle 9.3.1 wrapper JAR, Unix script, Windows script, and properties were generated by the downloaded Gradle 9.3.1 distribution in an empty temporary project, not by running the NYX app build. The distribution was verified against Gradle's published SHA-256 and the wrapper properties pin that checksum. The sandbox runs OpenJDK 21; the project's Java/Kotlin bytecode target remains 17.

### Installed SDK package evidence

The SDK command-line package catalog advertised Build Tools 36.0.0 and 37.0.0, NDK 28.2.13676358, CMake 3.22.1, and the API 37.0 platform. They were installed under `/home/ubuntu/Android/Sdk` on the verification date. The native build uses **NDK 28.2.13676358, CMake 3.22.1, C++17, `c++_shared`, and CMake target `nyx_llama`** at `app/src/main/cpp/CMakeLists.txt`.

The current command-line tools expose the base platform package as **`platforms;android-37.0`**, not `platforms;android-37`. The first attempt with the unsuffixed identifier reported package-not-found; inspecting the catalog and installing the correct identifier succeeded. This is a package-name change, **not proof of SDK 37 unavailability**, and does not permit an API 36 fallback. Installed platform metadata records `Platform.Version=17`, `AndroidVersion.ApiLevel=37.0`, `AndroidVersion.IsBaseSdk=true`, and revision 2.

```bash
SDK_ROOT="$HOME/Android/Sdk"
SDKMANAGER="$SDK_ROOT/cmdline-tools/latest/bin/sdkmanager"
"$SDKMANAGER" --sdk_root="$SDK_ROOT" --list
"$SDKMANAGER" --sdk_root="$SDK_ROOT" \
  'platforms;android-37.0' 'build-tools;36.0.0' 'build-tools;37.0.0' \
  'ndk;28.2.13676358' 'cmake;3.22.1'
```

The installed `sdkmanager` emits a deprecation notice and forwards SDK commands to the newer Android CLI; it still completed these installations. Build Tools 37.0.0 was additionally installed because the Android 17 setup page recommends the latest 37.x tools, but the app explicitly selects the supported AGP 9.1.1 default, 36.0.0. [2] [3]

## Target API policy and the permanent guard

Google Play's published policy requires ordinary phone/tablet **new app and app update submissions to target API 36 or higher from August 31, 2026**. The published extension ended November 1, 2026. Existing-app discoverability has a separate API 35 threshold; that does not authorize an API 35 update. NYX is not a Wear OS, TV, XR, or Automotive app and does not use their exception thresholds. [5]

`tools/check_sdk_policy.py` rejects target SDK below 36, compile SDK below target, changed minimum SDK, ambiguous/nonliteral assignments, and API 36 while the checked-in policy records SDK 37 as available. `:app:preBuild` depends on that Python checker and a separate Gradle check of the resolved Android DSL values. The Gradle variant callback additionally rejects target/minimum SDK overrides that evade `defaultConfig`. These checks are local and fail closed; builds do not fetch or infer a live Play policy.

```bash
python3 tools/check_sdk_policy.py
python3 tools/check_sdk_policy.py --self-test
python3 tools/check_sdk_policy.py --json
```

Before each release, re-open the official Play policy URL, re-evaluate deadlines and applicable device categories, and update the dated policy in the Python script, independent Gradle check, and this document together. API 37 is preferred and currently required because it is available. An API 36 fallback requires reproducible catalog/install evidence that the actual SDK 37 platform or necessary supported build tools cannot be obtained, a documented decision, and corresponding reviewed guard changes. Never lower below 36 or silently suppress an unsupported-SDK warning.

## Android 17 local network access

On Android 17, applications targeting API 37 or higher are blocked from local-network access by default and must declare and request the **`android.permission.ACCESS_LOCAL_NETWORK` runtime permission** before broad LAN access. It belongs to the Nearby devices permission group. It applies to outgoing and incoming TCP, UDP unicast/multicast/broadcast, `.local` name resolution, and framework/library/native networking including OkHttp. Denial or later revocation must stop LAN activity gracefully. Ordinary Internet and mobile-network traffic are unaffected. TCP permission failures can present as timeouts; UDP failures commonly report `EPERM`. [6]

An on-device JNI model does not need a LAN permission to perform CPU inference. A user-configured LAN inference server does. Gate the runtime check/request by device API 37; do not prompt solely because the app was compiled with API 37. System-mediated service selection can avoid broad access for the specifically selected device. Apps still targeting 36 or lower receive an implicit grant through `INTERNET` and should not request `ACCESS_LOCAL_NETWORK` under that legacy target. The Android 16 opt-in `RESTRICT_LOCAL_NETWORK`/`NEARBY_WIFI_DEVICES` instructions are explicitly deprecated for this API 37 migration. [6]

Android 17 also blocks **cross-profile loopback traffic by default for all apps**, independently of target SDK. Same-profile loopback is not affected by that particular change. This is a distinct restriction from LAN permission enforcement; do not assume localhost bridges across personal/work profiles work. [7]

## Memory admission and post-exit diagnostics

Android 17 introduces per-app memory limits based on device total RAM for **all apps running on Android 17**, not just target 37 apps. The official page does not publish a universal safe model size or a numeric per-app cap, and an app-controlled model admission budget is not the platform's enforced limit. Native allocations, model mapping, KV cache, Java heap, and other process working memory must be considered together. A foreground service is not a memory-limit exemption. [7]

For a session affected by the Android 17 limiter, inspect `ApplicationExitInfo`: the documented reason is **`REASON_OTHER`** and the description contains **`MemoryLimiter:AnonSwap`**. Do not mislabel this as `REASON_EXCESSIVE_RESOURCE`, `REASON_LOW_MEMORY`, or an invented `REASON_MEMORY_LIMIT` API. `ActivityManager.getHistoricalProcessExitReasons()` was added in API 30, returns recent deaths in a ring buffer, and must be SDK-gated on API 26–29 devices. Use a bounded count, inspect reason plus nullable description, and avoid claiming that absence of a retained exit record proves absence of a memory kill. [7] [8]

`ActivityManager.getMemoryInfo()` reports general **system** memory, not the private app's Android 17 cap. `availMem`, `lowMemory`, and `threshold` are available throughout NYX's supported range; `totalMem` was added in API 16. `advertisedMem` requires API 34 and differs from kernel-accessible RAM. New `freeMem` requires API 37 and is a snapshot of unused RAM excluding reclaimable memory; using it on API 26–36 requires a guard. `getMemoryClass()` is an approximate per-application class in MB, not a sufficient native LLM budget. Frequent polling is discouraged by the API reference. [8] [9]

NYX should conservatively refuse oversized native loads, limit context/batch/thread settings, release sessions on cancellation, persist recoverable state, and recognize limiter exits on the next launch. These are product safeguards, not promises against OS termination. On supported Android 17 devices, the official debug commands are `adb shell am memory-limiter status`, `adb shell am memory-limiter manual <pid> <limit-in-MB>`, and `adb shell am memory-limiter ignore <uid>|none|all`; commands have no effect on a device that does not impose limits. The status includes visible and non-visible limits. Do not disable production enforcement to mask a failure. [7]

## Native dynamic code loading

For apps targeting API 37 or higher, Android 17 extends Android 14's safer DCL protection from DEX/JAR files to **native files loaded with `System.load()`**. Such native files must be read-only or the system throws `UnsatisfiedLinkError`. The official guidance recommends avoiding dynamic code loading because it increases injection/tampering risk. [10]

Build the llama.cpp dependency into the APK's normal JNI library and load the packaged `nyx_llama` library with `System.loadLibrary`, rather than downloading an executable `.so` into writable app storage. GGUF model files and versioned skill/project documents are data, not executable plugin code; their import path must not load them as code. No mechanism should fetch arbitrary native/DEX/JAR plugins as a shortcut around this rule. [10]

## Foreground service semantics and timeouts

Foreground service types describe actual work, not the fact that an operation uses CPU or should remain alive. Android's `dataSync` description covers data transfer, backup/restore, imports/exports, fetching, and local file processing; this does not make an entire arbitrary compute or native inference loop a synchronization service. `mediaProcessing` covers media-asset operations such as transcoding, not text inference. A short critical operation may use `shortService`, but its approximately **three-minute** lifetime makes it inappropriate for a long model run. [11]

`specialUse` covers valid foreground use cases not covered by another type. It requires `FOREGROUND_SERVICE_SPECIAL_USE`, the `specialUse` service type, and a free-form explanation in the service's `android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE` property. Google Play reviews the declared explanation and corresponding use case. Declaring this type is **not a guarantee of Play approval**, permission to run indefinitely, or exemption from foreground-service start/lifecycle restrictions. [11]

When targeting API 35 or higher on Android 15+, background `dataSync` and `mediaProcessing` services have **separate six-hour budgets per 24 hours**, each shared by all app services of that type. Bringing the app to the foreground resets the timer. On exhaustion, the API 35 `Service.onTimeout(int, int)` callback allows only a few seconds to call `stopSelf()`; failure can produce a fatal internal service exception. The short-service timeout callback also exists on API 34 and has its own ANR consequences. Do not apply the six-hour dataSync limit to every foreground service or invent a platform 30-minute specialUse timeout. [11] [12]

A **30-minute NYX run deadline**, if implemented, is an app-level engineering bound. Stop/cancel must interrupt generation cooperatively, release native state, and call `stopSelf()` on completion, cancellation, failure, and timeout. Keep a user-visible notification and cancellation control; initiate runs from explicit user action. Handle both platform `onTimeout` overloads where applicable, even though native compute is not classified as dataSync. The timeout page supplies compat/debug commands for dataSync/mediaProcessing tests; use the app's own deadline and lifecycle tests for specialUse behavior. [11] [12]

## 16 KB native packaging and validation

AGP 8.5.1+ correctly 16 KB zip-aligns uncompressed shared libraries, and **NDK r28+ generates 16 KB ELF alignment by default**. NYX's newer pinned toolchain and `useLegacyPackaging = false` therefore provide the required build configuration. Every bundled native dependency, including `libc++_shared.so`, must also satisfy alignment. Do not hard-code 4096-byte page assumptions; query the actual page size where page granularity matters. The official guidance distinguishes packaging alignment, ELF segment alignment, and runtime correctness. [13]

After a serialized app build, extract the actual APK and check **every** packaged `.so` with the NDK's `llvm-objdump -p`: `LOAD` alignments must not be below `2**14`. Then run:

```bash
"$ANDROID_HOME/build-tools/36.0.0/zipalign" -v -c -P 16 4 \
  app/build/outputs/apk/debug/app-debug.apk
```

For an AAB, `bundletool dump config --bundle=<bundle.aab>` should report `PAGE_ALIGNMENT_16K`. Static configuration alone does not prove a produced APK is aligned, nor that the native model path works on a real 16 KB device. [13]

No physical-device execution, native inference throughput, memory-cap survival, permission prompt, service-lifecycle behavior, thermal behavior, or 16 KB runtime compatibility is claimed in this document. Record the exact device/OS/page size/model and test outcome separately when those tests are actually performed.
